Deliverables:

- CAPEX milestones/events.
- OPEX milestones and installment schedule generator.

- Idempotency registry.

Exit criteria:

- OPEX schedule totals reconcile exactly.
- Posting engine cannot write an unbalanced journal.
- No invoice/receipt UI yet writes finance data outside the posting engine.

Sub-phase progress:

- **4.1 — Chart of Accounts: complete.** New `AccountGroup`/`LedgerAccount` models — the root of the entire accounting subtree everything else in this phase depends on. `accountType`/`normalBalance` stored explicitly on every group (root and custom), inherited by a custom group from its parent at creation, never independently entered; re-parenting only permitted to a classification-compatible active parent, with direct and indirect cycle rejection. The five system-defined roots (Assets/Liabilities/Equity/Income/Expenses) are permanently fixed (code/type/normalBalance/parent immutable, never deactivatable); every custom group requires an active parent. `chart_of_account.read`/`chart_of_account.manage` permissions (Admin/Accountant/CEO-read). One page under a new "Finance" nav group — Account Groups and Ledger Accounts, one drawer each, derived classification always shown read-only. See ADR-062 and the matching docs/13-progress.md entry. No journal entries, posting engine, opening balances, reconciliation, or seeded leaf ledger accounts this slice — disclosed scope boundaries, not gaps.
- **4.2 — CAPEX/OPEX Milestones: complete.** New `ProjectMilestone`/`MilestoneEvent`/`MilestoneInstallment`/`MilestoneCreationRequest` models with database-enforced type-safe FKs (an event can never reference an OPEX milestone, or vice versa) and twelve hand-added `CHECK` constraints. Codes (`CAP-001`, `CAP-001-E01`, `OPEX-001`) are entirely server-generated, retry-safe under concurrency. CAPEX event amounts must sum to the pool's approved amount exactly (backend-enforced on create and edit); `percentOfPool` is always derived. Full achievement lifecycle (`start`/`markAchieved`/`cancel`, no stage-skipping) for both CAPEX events and OPEX milestones, with cancelling an OPEX milestone cascading every remaining planned installment to cancelled. OPEX schedule generation uses one pure, backend-authoritative generator (`Prisma.Decimal` throughout, calendar-safe end-of-month clamping, independent service-period/invoice-date sequences) shared by the preview query, the real create mutation, and the tests. New `milestone.skip_installment` permission; Accountant gets create/update/skip (finance-maintained schedules), Project Manager gets mark_achieved/cancel (delivery execution) — a deliberate departure from `Project`'s own Admin-only create precedent. Idempotent, atomic creation via a client-supplied key. One "Milestone" project tab — CAPEX/OPEX sections, live running-balance blocking Save, server-driven schedule preview. Backend tested (170 integration tests); UI subsequently verified by the user in a live browser pass. See ADR-063 and the matching docs/13-progress.md entry. No Payment Alerts, invoices, receipts, journals, or postings this slice — disclosed scope boundaries, not gaps.
- **4.3 — Payment Alerts: complete.** New unified `PaymentAlert` model (one row per CAPEX event or OPEX installment, ever — `sourceEventId`/`sourceInstallmentId` hard-unique) with a CHECK-enforced source-type/FK match. No stored amount/due-date copy — always read live from the source, so an in-flight edit is never stale. The first slice driven by a recurring background job: a new `apps/worker` alert-opener ticks every 15 minutes, opening a CAPEX event's alert once it's past due or marked achieved (whichever comes first) and an OPEX installment's alert once past its reminder-offset window, reopening snoozed alerts once their window passes, and notifying resolved recipients through the existing outbox/notification pipeline (`ACCOUNT_TEAM` resolves to every user whose effective permissions include `payment_alert.snooze`, not a hardcoded role). Cancelling/skipping a CAPEX event or OPEX installment now also deletes its live alert — the one deliberate exception to this codebase's no-physical-deletion rule, since a dead alert for a billing event that will never happen isn't a financial record. New `payment_alert.read`/`payment_alert.snooze` permissions (Accountant gets both, Project Manager read-only). One "Payment Alert" project tab — summary tiles, Open/Snoozed sections, a Snooze modal, and a disabled "Raise Invoice" placeholder tooltipped as Phase 5 work. UI subsequently verified by the user in a live browser pass. See ADR-064 and the matching docs/13-progress.md entry. No invoice creation, journals, or postings this slice — disclosed scope boundaries, not gaps.
- **4.4 — Journal Entries, Posting Engine, Idempotency Registry, Period-Lock Enforcement: complete.** New `JournalEntry`/`JournalLine` models implementing `docs/06-accounting-posting-rules.md`'s frozen structure verbatim (every dimension named — ledger account, debit/credit, project, party, employee, GST registration, tax code, narrative — even though no current caller populates most of them yet). A single `postJournal` method enforces every mandatory posting control in one atomic transaction: zero-line/negative-amount/both-or-neither-debit-credit/unbalanced rejection, accounting-period resolution with a snapshot FK (a posting's period is a permanent historical fact), `LOCKED`-period rejection (`SOFT_CLOSED` still accepts a posting — confirmed with the user), inactive/non-postable ledger account rejection, and duplicate-source-event rejection. Idempotency reuses an existing, previously-undiscovered generic `IdempotencyKey` model from the Phase 1 foundation (already used by `UsersService.invite`) rather than a new table — a self-caught correction to this slice's own plan mid-implementation. `postJournal` has no tRPC procedure at all — posting occurs only at approved business events, called by other backend services once one exists (EMD/SD is the first real caller — see 4.5). New `journal.read` permission (Admin/Accountant/CEO). Two read-only UI surfaces under "Finance" — a new Journal Entries list/drill-down page, and a "View Ledger" running-balance drawer added to the existing Chart of Accounts page — together completing the "Chart of Accounts and Ledger Viewer" `NEW_REQUIRED` screen docs/04 names, which 4.1 only half-built. UI subsequently verified by the user in a live browser pass. See ADR-065 and the matching docs/13-progress.md entry. No reversal (see 4.6), no manual journal entry creation this slice — disclosed scope boundaries, not gaps.
- **4.5 — EMD/SD (Security Instruments): complete.** New `SecurityInstrument` model — `postJournal`'s first real caller. Lodging a cash-equivalent instrument (cash/DD/FDR/banker's cheque/online payment) posts Dr Recoverable / Cr Bank per `docs/06`; a guarantee instrument (bank guarantee, insurance surety bond) posts nothing, tracked only as contingent exposure. A full return (received amount must equal the lodged amount exactly — penalty-deducted returns are deferred) posts the mirror entry and transitions `LODGED → RETURNED`; "Return Due" is a derived label (`returnDueOn` passed, still `LODGED`), not a stored third state. May reference a Project, a Tender, or both (ADR-020) — at least one is required. The prototype's plain "Funded by Primary Company?" toggle was reshaped, per the user's own follow-up question, into a structured funding-entity capture (Legal Entity or Party, plus bank-account details) on both the lodge and return sides — informational only, no inter-company posting is invented. `SecurityInstrumentPurpose` gained a nullable `category` (EMD/SD, drives the list screen's tiles) and a per-purpose default recoverable ledger account; `SecurityInstrumentType` gained `requiresCashPosting` plus a new `cash` row. Four new permissions (`security_instrument.read/create/post/export`) mirroring the live `milestone.*`/`payment_alert.*` grant pattern exactly. Three UI surfaces: a global `/emd-sd` list with five server-computed summary tiles, a lodge Drawer, a Record Return modal (no prototype — built fresh), and a new "EMD / SD" project tab. UI subsequently verified by the user in a live browser pass, including a real end-to-end lodge → journal-posting confirmation. See ADR-066 and the matching docs/13-progress.md entry. No BG margin/commission/GST postings, no inter-company payable posting, no penalty-deducted returns this slice — disclosed scope boundaries, not gaps.
- **4.6 — Reversal Mechanism: complete.** Makes the already-reserved `JournalEntryStatus.REVERSED` value reachable for the first time. `reverseJournal` creates a new, opposite-signed `JournalEntry` referencing the original (`reversalOfJournalEntryId`, a single-column self-relation FK) and flips the original to `REVERSED` with a required reason/actor/timestamp, atomically in one transaction — the original's lines are never edited or deleted, per `docs/06`'s "posted journal entries are immutable... reversal entries reference the original entry." The reversal's own accounting date is independent of the original's, so a reversal always lands in whatever period is open today even if the original's period has since been `LOCKED`. Unlike `postJournal`, `reverseJournal` is a direct, human-triggered correction action with a real tRPC procedure — the first posting-adjacent end-user mutation in this app. No maker-checker restriction (confirmed with the user) — any Accountant/Admin holding the new `journal.reverse` permission may reverse any posted entry, including their own. Reversing a reversal is allowed (not specially blocked), matching standard accounting practice. UI: a "Reverse" row action and modal on the existing Journal Entries page, plus bidirectional reversal links in its entry-detail drawer — no new route. UI subsequently verified by the user in a live browser pass. See ADR-067 and the matching docs/13-progress.md entry. No credit/debit notes, no source-business-record correction (e.g. reversing an EMD lodge journal never reverts the `SecurityInstrument` row itself), no partial/amount-adjusted reversal this slice — disclosed scope boundaries, not gaps.

**Phase 4 is now fully COMPLETE** — all six slices (4.1–4.6) have shipped their backend/decisions, and UI verification for 4.2 through 4.6 was subsequently confirmed by the user in a live browser pass (4.1 had already completed full verification earlier). No outstanding verification gaps remain in Phase 4.

## Phase 5 — Finance income vertical slice

Implement end-to-end:

`Milestone/Installment → Alert → Invoice → Receipt → Deductions → Journal → Bank Match`

Deliverables:

- Invoice drafts, numbering, finalization, PDF, and snapshots.
- Credit/debit note and void/replacement foundation.
- Client receipts with multi-invoice allocation.
- Partial receipt.
- TDS and GST-TDS.
- Hold/retention and releases.
- Accepted/disputed penalties.
- Bank transaction entry/import and reconciliation.
- Ledger account opening balances (a starting Dr/Cr figure as of a given date per legal entity/ledger account) — a prerequisite for real bank reconciliation, and for the Ledger Viewer (Chart of Accounts' "View Ledger" drawer, Slice 4.1/4.4) to show a true running balance instead of one computed from a zero baseline. Once this exists, revisit the Ledger Viewer's UI toward the richer reference design raised during Slice 4.5 verification — an "Account view"/"Journal view" toggle, an opening-balance banner, Export, and an expandable per-row balanced-journal-entry detail — rather than today's single flat activity table.
- Invoice/payment/project read models.

Exit criteria:

- All four priority HTML screens are implemented with documented minor changes.
- Golden finance tests pass.
- Source documents, journals, and reports reconcile.

Sub-phase progress:

- **5.1 — Invoice (Draft, Finalize, Void): complete — implementation and UI both verified.** New `Invoice`/`InvoiceLine` models — every invoice originates from a `PaymentAlert` via `createDraftFromAlert`, no free-standing creation (docs/04: "remove free ad-hoc invoice creation"). At most one active (non-void) invoice per `MilestoneEvent`/`MilestoneInstallment` at a time (partial unique indexes), extending OPEX's "one active finalized invoice, voided one replaceable" rule to CAPEX events too. `PaymentAlertStatus` gains `CLOSED` (closing ADR-064's disclosed gap); `InstallmentStatus` gains `INVOICE_DRAFT`/`INVOICED`. Finalize computes CGST+SGST (same state) or IGST (different state) per line, hand-entered GST rate/HSN-SAC (no rate master this slice), snapshots seller/buyer immutably, server-generates the invoice number (scoped to GST registration + financial year, retry-safe under concurrency, same pattern as Milestone codes), calls the existing `postJournal` (Dr Accounts Receivable; Cr Project Revenue + Output CGST/SGST/IGST Payable — three new ledger accounts), and closes the source alert. Enforces the CAPEX milestone approved-amount cap across all its events' finalized invoices. Void of a draft is a status flip; void of a finalized invoice calls the existing `reverseJournal` (Slice 4.6, its first real caller outside its own tests), reopens the source alert, and reverts the installment status. PDF generated on demand via `pdfkit`, never persisted as a file. Six new permissions (`invoice.read/create/update/finalize/void/export`) mirroring the `milestone.*`/`payment_alert.*`/`security_instrument.*` grant pattern exactly, with PM/Admin Staff read-scoped to their assigned projects. UI: the Payment Alert tab's "Raise Invoice" button now navigates to a real add form; a dedicated (non-Drawer) invoice add/edit route; a project "Invoices" tab and a global `/invoices` list, neither carrying an Add button (creation is alert-only). See ADR-068 and the matching docs/13-progress.md entry. No Receipt/Deductions/Bank Match, no Credit/Debit Note, no Vendor Bill, no GST/HSN rate master this slice — disclosed scope boundaries, not gaps.
- **5.2 — Client Receipt (multi-invoice allocation, typed deductions, hold/retention release): complete — implementation and UI both verified.** New `BankAccount` master (folded into the existing `LegalEntityService`, a legal-entity sub-resource reusing `legal_entity.*` permissions, matching GST Registrations) and `ClientReceipt`/`ReceiptAllocation`/`AllocationDeduction`/`DeductionRelease` models. `receipt.post` is one atomic action (no draft/finalize split) allocating a single bank receipt across one or more `FINALIZED` invoices belonging to one client and one legal entity, with per-allocation typed deductions (TDS, CGST/SGST/IGST-TDS, hold, retention, accepted/disputed penalty, other) resolved to their own ledger accounts (seven new accounts, one new `OTHER_RECEIVABLES` group) and posted as one combined docs/06 journal — Dr Bank + each deduction account; Cr Accounts Receivable. Invoice/deduction outstanding amounts are always computed live, never stored, matching Payment Alert's "always read live" precedent. `receipt.reverse` reuses `reverseJournal` (Slice 4.6) without mutating the allocation/deduction history. `deduction.release` posts the docs/06 hold/retention mirror entry and supports repeated partial releases. Cash must fully allocate across invoice rows this slice — an "unallocated/on-account" balance is named in docs/03 but has no defined posting treatment in docs/06, so it's deferred rather than invented. Four new permissions (`receipt.read/post/reverse`, `deduction.release`) mirroring the `invoice.*` grant pattern. UI: the invoice detail page's "Record Payment" action opens a dedicated add-form (multi-row invoice allocation + nested typed-deduction editor) that shows zero client-computed settlement math — a `calculatePreview` query renders the server-computed breakdown on demand; a project "Payment" tab and global `/payment-integration` list mirror Invoice's own shape; a new `/bank-accounts` master screen. See ADR-069 and the matching docs/13-progress.md entry. No Bank Transaction Import/Reconciliation/Matching, no Credit/Debit Note, no TDS Certificate/26AS reconciliation this slice — disclosed scope boundaries, not gaps.
- **5.3 — Credit Note / Debit Note: complete — implementation and UI both verified.** New `CreditDebitNote`/`CreditDebitNoteLine` models (`type: CREDIT|DEBIT`) correct an already-`FINALIZED` invoice without voiding it — `invoiceId` is not unique (an invoice may receive many notes over time), and the source invoice's own status/`PaymentAlert` are never touched. Finalize posts the mirror of `Invoice.finalize`'s own journal (Credit Note: `Dr Project Revenue + Output GST / Cr Accounts Receivable`; Debit Note: the same direction as `Invoice.finalize` itself), always into whatever accounting period is open *today* — never the original invoice's own, since-possibly-`LOCKED` period, matching the Reversal Mechanism's own precedent (ADR-067). Cumulative Credit Notes against one invoice are capped at that invoice's taxable amount, mirroring the CAPEX-milestone-cap precedent; Debit Notes are uncapped. Independent `CN-0001`/`DN-0001` numbering series, scoped like Invoice numbering plus `type`. - **7.2 — Stock ledger, weighted-average valuation engine, Vendor Bill inventory variant: complete and database-verified.** Promotes **TDR-007 to Accepted** with rationale: weighted average is the only candidate method needing no per-unit or per-lot identity — FIFO/LIFO would require lot tracking docs/00 excludes outright, and specific identification is meaningless for consumables and cabling. One pure `inventory-valuation.util.ts` holds the whole arithmetic, shared by every caller and the tests. **Full depletion carries out the entire remaining value**, not `quantity × rate` — without that special case an uneven rate strands paise against zero quantity forever and stock value permanently stops reconciling to the INVENTORY account, failing this phase's own exit criterion silently. `InventoryMovement` is append-only and stamps the balance it produced onto every row, so a past consumption's cost stays reproducible and the sum of every item's latest `balanceValueAmount` **is** the INVENTORY account balance — the exit criterion holds by construction, not by a reconciliation job. Backdated movements are refused (they would invalidate every later stamped rate); correction is reversal then re-entry, the same posture a posted journal has. `InventoryLedgerService.recordMovement` is the single writer, always taking the item's row lock first and always running inside the caller's own transaction (docs/02's "post inventory receipt/consumption + cost entry" boundary). Vendor Bill closes ADR-075's disclosed "no inventory variant" gap: a line is now either an expense line or a stock line (nullable `expenseCategoryId`, new `inventoryItemId`, DB CHECK enforcing exactly one), `approve()` branches the debit account while deliberately **sharing** the `costDebit` formula (docs/06's two tables debit the identical figure and differ only in the account), and the movement is created in the same transaction — never a second journal (docs/04:464). `InventoryReceipt` covers only what the bill path cannot: OPENING (reusing ADR-071's opening-balance mechanism) and DIRECT. Stock adjustments and write-offs are deliberately not built — docs/06 gives them no posting rule, so they are deferred rather than invented.
